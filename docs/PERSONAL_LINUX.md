# Личный Linux на сервере

Решение владельца, 3 октября 2026. Доступ получают приглашённые близкие друзья
и сотрудники. Это самостоятельное личное окружение для файлов, сайтов, ботов,
пакетов и постоянно работающих служб. Владелец 4 октября уточнил: встроенный Codex
из старого окружения убрать. В образе и автоматических проверках его больше нет;
личный Linux не предлагается как машина чатов Codex. Ручная установка собственных
инструментов пользователем в будущем системном Linux — отдельная свобода, не
обязательное условие готовности.

## Пользовательский контракт

Уточнение 4 октября: аккаунт владельца установки уже имеет прямой полный доступ
к серверу. Ему не предлагается отдельное личное окружение и не добавляется его
дублирующее устройство. Прежний диск и записи сохраняются. Приглашённые пользователи
получают изолированный Linux; роль администратора Hub сама по себе не даёт им доступ
к хосту и не отменяет изоляцию.

- SSH/SFTP по своему ключу через VPN/Tailscale. Проброс портов роутера не нужен.
  Вход только в собственный Linux; права на хост и остальные узлы Tailnet не выдаются.
- Администратор внутри непривилегированного системного контейнера. Установка
  пакетов и настройка systemd-служб не требуют обращения к владельцу сервера.
- Постоянные файлы и службы; закрытие браузера, отсутствие Hub, остановка чата
  или выключение личного ПК не завершают пользовательские сервисы.
- Ограничения CPU, RAM, диска, числа процессов и скорости сети. Отдельно ограничен
  общий бюджет, чтобы окружения не вытеснили работающие на хосте приложения.
- Публикация HTTPS-сайта — отдельное действие с точной привязкой владельца,
  имени и сервиса. Наличие SSH не публикует все его порты. Прочие порты выделяются
  отдельно; host network и произвольные host mounts пользователю недоступны.
- Прямого доступа к домашней сети, хосту, соседним окружениям и сокетам управления
  нет. Явно выданный совместный доступ не означает снятие этих границ.
- Резервные копии и восстановление относятся к окружению и привязке владельца,
  а не только к базе Hub. Сохранять три завершённых проверенных копии каждого потока.
- Собственный Docker надо проверить отдельно как функцию вложенных контейнеров.
  До этого не показывать его готовым и не включать privileged ради совместимости.

## Companion отвечает за подключённое устройство целиком

Уточнение владельца: Companion обеспечивает связь, файлы, терминал, сервисы,
обновления, диагностику и ограниченное восстановление. Codex и другие интеграции —
его возможности, а не обязательное условие готовности всей системы.

Общий контракт для Windows и будущего Linux-адаптера:

| Возможность | Собственные условия готовности |
| --- | --- |
| Связь и привязка | Точный Hub account/device, выбранный маршрут LAN/Tailscale |
| Файлы и терминал | Доступный транспорт, авторизованные каталоги/окружение |
| Пользовательские службы | Состояние локального менеджера служб и конкретного сервиса |
| Codex | Установленный необязательный компонент, его собственный вход и состояние |
| Git/GitHub, браузер, Remote, Computer Use | Собственные зависимости и права для выбранной возможности |
| Обновления и восстановление | Проверенный пакет, состояние именно затрагиваемого компонента |

Отсутствие Codex или его авторизации не скрывает файлы, терминал и серверные
службы. Не выводить единый «всё сломано» из отказа одной интеграции. Не запускать
постоянные проверки модели/GPT ради базовой готовности машины. Обновление компонента
не перезапускает независимые сервисы. Потеря подтверждения не повторяет команду.

На управляемом сервере не требуется графический трей в каждом контейнере.
Используется общий контракт возможностей и закрытый серверный адаптер. Прямой
SSH и systemd продолжают работать без Hub или приложения на пользовательском ПК.
Пользовательскому контейнеру нельзя выдавать административный Incus API или ключ Hub.
Текущее `apps/companion/Readiness.cs` уже разделяет компонентные состояния;
это основа, но не доказательство готовой интеграции личного Linux.

## Технический переход

Подготавливается Incus с отдельными project/network/storage pool. Это не изменение
флагов работающего Podman-контейнера. Системный контейнер использует ядро хоста;
не обещаем невозможность выхода при любой уязвимости. Особые задачи с собственным
ядром/более сильной изоляцией потребуют отдельного решения о виртуальной машине.

Первоначальный профиль: 2 CPU, 2 GiB RAM без swap, 512 процессов, 16 GiB корневой
диск, сеть до 100 Mbit/s. Общий лимит нового проекта: два контейнера, 4 GiB RAM,
4 CPU и 1024 процесса. Отдельный Btrfs loop pool ограничен 48 GiB, включая образы
и служебные расходы. Это стартовые ограничения по наблюдавшейся загрузке сервера,
а не неизменяемый тариф. Старые четыре диска по 16 GiB остаются нетронутыми.

Подсеть `10.203.0.0/24` проверяется на пересечение с действующими маршрутами.
У каждого контейнера отдельная карта UID/GID; root гостя не является root хоста.
Новый firewall относится только к `cwpersonal0`. Разрешены публичный IPv4 и ответы
на инициированные хостом соединения, закрыты новые обращения к хосту/LAN/Tailnet,
соседи, IPv6 и незапрошенный маршрутизируемый вход. DNS гостя — публичный.
Incus API остаётся на локальном Unix socket; права пользователя ОС не расширяются.

Источники: [безопасность Incus](https://linuxcontainers.org/incus/docs/main/explanation/security/),
[ограниченные проекты](https://linuxcontainers.org/incus/docs/main/reference/projects/),
[системные контейнеры и VM](https://linuxcontainers.org/incus/docs/main/explanation/instances/).

## Что подготовлено и что ещё не включено

`ops/personal-linux` — администраторская подготовка и настоящая проверка на двух
временных контейнерах. Она устанавливает пакеты Ubuntu, отдельную сеть/пул/профиль,
проверяет пакеты, systemd, ключевой SSH, точный SFTP, сохранность после перезапуска,
UID/cgroup/seccomp, недоступность реально слушающих хоста/соседа и ENOSPC.
Тест не использует личные аккаунты, старые диски или native writers.

Это **не готовая миграция и не пользовательская активация**. Требуются:

1. Выполнение подготовленного системного шага с sudo и успешная реальная проверка.
2. Встраивание Incus в существующий owner-bound broker и общий контракт Companion;
   независимые операции/состояния, управление ключами и точным VPN-маршрутом.
3. Проверенный backup/restore, явный перенос существующих данных с сохранением
   старого окружения для отката, затем подключение новой машины в Hub.
4. Публикация сервисов, пользовательские операции с ними и проверка вложенного Docker.

Не переключать подключение и не обещать готовность по одному успешному dry-run.
Автозапуск новых личных окружений включать при их активации; временные проверки
имеют `boot.autostart=false`. Windows Companion этим пакетом не обновляется.

## Удаление прежнего встроенного Codex — 4 октября

Hub отключает компонент Codex у личного окружения, сохраняя его транспорт,
терминал и файлы. Старые записи проектов не удаляются; автоматический каталог,
опрос активности и запуск app-server для этого устройства прекращены.
`ops/workspaces/remove-bundled-codex.py` применяет подготовленный проверенный образ
без Codex к точному владельцу: проверка простоя именно контейнеров окружения,
сохранение старого контейнера и реестра, неизменный пользовательский диск,
проверка образа и откат при ошибке. Скрипт ограничен этим инцидентом RECEIPTS_FULL:
перед остановкой broker проверяет, что тот не может принимать новые команды.
Hub, другие чаты и терминал хоста не останавливаются.
Нужен root хоста; это не установка Incus и не заявление о готовности VPN SSH.

Обнаруженный RECEIPTS_FULL исправляется ограниченной очисткой подтверждённых
старых записей вне времени действия capability. Accepted/unknown сохраняются
на прежний срок; повторное выполнение команд не производится.
