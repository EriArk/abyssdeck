Новая версия подготовлена и проверена отдельным read-only app-server, но это
не подтверждает переключение работающего Companion. Он обслуживает текущие чаты.
Подготовлена ограниченная четырьмя часами операция переключения после native-idle:
штатный Hub maintenance acquire → подтверждение отсутствия дочернего native
процесса → остановка только его брокера → атомарная смена config → запуск той же
задачи → Hub release с проверкой сохранённого аккаунта → проверка пути процесса.
При неопределённом результате операция останавливается с журналом; сообщения
не переотправляются и неизвестные эффекты не повторяются.

Фактический результат смотрится отдельно в:
`%LOCALAPPDATA%\CodexWeb\companion-persistent\updates\0.162.1\state.json`.
Только `activated` подтверждает завершённое переключение. `waitingIdle` означает
ожидание, `expired` — отсутствие простоя за четыре часа без смены config,
`needsInspection` — необходимость разобрать сохранённый результат. Предыдущие
config/journal сохраняются рядом при замене; старый runtime остаётся доступен.
Не запускать вторую операцию, пока не проверен этот журнал и durable lease Hub.

## Пути и причина отставания

Companion намеренно удерживал snapshot `runtime\c6fe824d725f02d7\codex.exe`.
Обновление Store-приложения не меняет эту привязку. Это защищало выполняющиеся
чаты от исчезновения нового hash-каталога приложения, но оставило CLI на 0.159.2.
Старый `Copy-CompanionRuntime.ps1` рассчитан на плоский набор исполняемых файлов.
Новый официальный полный пакет имеет `bin`, `codex-resources`, `codex-path` и
ресурсы voice; для него одного копирования EXE недостаточно.

`ops/windows/Stage-CodexRuntime.ps1` теперь подготавливает **полный** пакет в одном
корне `%LOCALAPPDATA%\CodexWeb\companion-persistent\runtime\<version>`. Повтор
той же версии проверяет receipt, manifest, полный список и хеши файлов, затем
возвращает тот же путь. Он не создаёт ещё одну копию и не меняет работающий процесс.
Другой layout, пропавшие файлы, изменённое содержимое и ссылки вместо каталогов
отклоняются. Официальные metadata и digest проверяются перед извлечением.

Пример следующей подготовки:

```powershell
& .\ops\windows\Stage-CodexRuntime.ps1 -Version latest
```

Это подготовка, а не самостоятельная команда активации. Переключение требует
штатной проверки простоя. Встроенную установку Store и её каталоги WindowsApps
не переносили: ими управляет Windows. Общий стабильный корень не означает
перезапись занятого EXE; активная и резервная версии должны временно сосуществовать.
Глобальная установка ещё одного CLI в PATH не выполнялась.

Старые используемые runtime, браузер, Computer Use и Companion UI не удалялись.
Второй каталог OpenAI/Codex/bin с `rg.exe` не является второй копией Codex.
Автоматическая очистка старых staged CLI-пакетов пока **не реализована**; при
дальнейшей интеграции обновлятора нужно удерживать последние три проверенные
версии и дополнительно все занятые/выбранные версии. Установку в одну папку нельзя
выдавать за уже выполненную общую очистку диска.

## Проверки совместимости

- Через существующий `packages/codex` adapter с 0.162.1: initialize,
  account/read, model/list (7 моделей), thread/list, thread/read metadata,
  thread/turns/list и thread/items/list (по одной записи с cursor), MCP inventory,
  command/exec с настоящим PowerShell и exit code 0. Новых чатов/ходов не создавали.
- В сравнении экспортированных JSON-схем 0.159.2 → 0.162.1 старые RPC-методы
  сохранены. Добавлен `thread/attachmentOwner/list`. Обнаружено удаление поля
  `ModelProviderCapabilitiesReadResponse.namespaceTools`; использования его в
  AbyssDeck не найдено. Это ограниченное сравнение, не доказательство совместимости
  всех вложенных enum и всех событий.
- 30 существующих регрессионных тестов runtime binding, maintenance, native Plan,
  public work и Results прошли. Новый Windows-тест staging проверяет повторный
  запуск, неверную версию/корень, испорченный файл, неполный receipt, пропавший
  компонент, неподдерживаемый layout и подмену каталога ссылкой.
- Public `agentMessage.phase` сохраняется адаптером. Существующие потребители
  финальных результатов выбирают именно `final_answer`: появление `partial_answer`
  само по себе не должно завершать ход или публиковать итог. Полный сценарий новой
  фазы с реальной генерацией в этой проверке не воспроизводился.

## Что стоит добавить или проверить в AbyssDeck

1. **Приоритет: совместимость истории и вложений.** Использовать новый
   `thread/attachmentOwner/list` и lineage/root-turn IDs там, где нужна точная
   принадлежность файла или ответа. Проверить fork/resume, скрытые/архивные чаты,
   одинаковые имена файлов, постраничную загрузку и восстановление после обрыва.
   Это предложение, API ещё не интегрирован.
2. **Приоритет: новые фазы ответа.** Добавить fixture нового `partial_answer` во
   все общие границы: transport → durable history → Chat/Results → notifications.
   Промежуточный публичный ответ должен сохраняться, но не становиться финальным
   отчётом. Проверять на наборах событий, не на одном скриншоте.
3. **Приоритет: упаковка и обновление.** Подключить полный staged package к
   штатному Companion update workflow с проверкой схем, native-idle, receipt,
   подтверждённой активацией, восстановлением и retention. Текущая подготовка
   пакета и разовая операция не означают, что весь wizard уже использует её.
4. **После этого:** native managed worktrees, pinned agent tasks и ranked tool
   search/Code Mode streaming могут быть полезны для проектов и больших наборов
   инструментов. Сначала сопоставить их с существующими worktree/Goals/Results,
   чтобы не создавать второй независимый механизм.

В 0.160–0.162 также появились исправления очередей/неопределённых продолжений,
Windows PowerShell и длинных путей, свежего чтения истории при resume, CRLF в
apply_patch, Retry-After и многострочных async-вопросов. Они полезны без новых
кнопок в AbyssDeck. Обновление не доказывает устранение всех прежних HTTP 400:
ограничение объёма image-heavy истории и компактные handoff остаются актуальными.
