# Повторная проверка отправки, синхронизации и инструментов

Проверена установка Hub `1e22073`, исходники `3f8e06a` и новая правка.
Предыдущие исправления из WORKFLOW_AUDIT_2026-10-01.md повторно не внедрялись.

## Две воспроизведённые ошибки

1. **Принятая запись очереди остаётся после восстановления истории.** Живое
   событие `userMessage` уже очищает её независимо от браузера. Однако после
   пропуска события `Catalog.history` удалял только `enqueue_pending/unknown`,
   оставляя `queued/steered`. Пользователь мог одновременно видеть доставленное
   сообщение и старую плашку, а фоновое задание — ждать эту запись.
   Теперь канонический user item снимает подтверждённую плашку по точному client ID
   в том же чате. Неопределённые изменения очереди, другие сообщения и другие
   чаты сохраняются. Нового native вызова или повтора ввода нет.
2. **Вложение оставалось заблокированным после отказа до отправки.**
   `syncQueueInstructions` находился вне `try/finally` подготовленных вложений.
   При его ошибке файл оставался в `protectedIds`, и удаление из черновика
   возвращало `ATTACHMENT_IN_USE`. Освобождение теперь выполняется и на этом пути.
   Файл и текст не отправляются; привязка к сообщению не создаётся.

Обе проверки падают на установленном образе `1e22073` и проходят с исправлением.
Отдельная проверка обычного события без единого чтения очереди проходит и на старой
версии: первоначальная гипотеза о зависимости всех фоновых отправок от открытого
веба не подтвердилась. Исправлен конкретный путь восстановления истории.

## Остаток для следующих этапов

- Ежедневный `ops/workspaces/checkpoint.py` всё ещё держит gateway/engine выключенными
  во время копирования и проверки. Оптимизация backup при обновлении не покрывает
  эту службу. Требуется отдельная подготовка снимка, короткое согласованное окно и
  замер доступности. Занятый lock также пока попадает в общий обработчик ошибки.
  Текущая служба inactive/result=success; её код из этого выпуска не устанавливался.
  На сервере `sudo -n` требует пароль, значит установка root-owned службы должна
  пройти через существующий приватный терминал владельца.
- Истории с user без final остаются в ограниченном списке фонового наблюдения.
  Это read-only polling, а не доказательство работы GPT. Стоит отдельно проверить
  снижение частоты для давно неизменных ответов, сохранив обнаружение позднего final.
- Схема `thread/queue/add` не содержит `additionalContext`; подсказка маршрутизации
  подаётся через `turn/start`. Неподдерживаемое поле в очередь не добавлялось;
  инструкции Plan не подменялись. Отсутствие подсказки само по себе не означает
  отсутствия MCP: текущий вызов встроенного браузера успешен.

Два прежних локальных изменения Companion/миграции workers сохранены вне выпуска.
Аудит не является заявлением о проверке каждого экрана и каждой машины.
